## 1. Почва и размножение культуры

**Статус:** отложено, не реализуем сейчас.
**Дата обсуждения:** 2026-09-23.

### Проблема

В ответах AI отсутствует информация о:
- рекомендуемой почве для культуры (тип, кислотность, дренаж);
- способах размножения (семенами, черенками, делением, сроки).

Это базовая информация, которую пользователь ожидает увидеть в справочнике.

### Рассмотренные варианты

| # | Вариант | Работы | UX | AI-стоимость | Лишние запросы |
|---|---------|--------|-----|--------------|----------------|
| 1 | Добавить разделы в существующий `care` | мин. | просто | +30% | нет |
| 2 | Новые кнопки на `CultureDetailScreen` | средне | чётко | та же | +2 запроса |
| 3 | Отдельный экран «О культуре» (не AI) | много | отлично | ~0 (кэш) | нет |
| 4 | Блок `## Основное` в начале `care` | мин. | просто | +10% | нет |
| 5 | Группы кнопок: «Уход» / «Информация» | много | чётко | та же | +3 запроса |

### Рекомендация (на момент обсуждения)

**Комбинация 1 + 4:** в промпт `care` добавить компактный блок `## Основное`
в начале ответа:

    - Почва: рыхлая, плодородная, pH 6,0–6,8
    - Размножение: семенами через рассаду, срок — март
    - Сроки вегетации: 100–120 дней

Углублённые вопросы — через `free`-промпт в «Справке AI».

Позже, при наличии обратной связи от пользователей — переход к варианту 3
(отдельный экран «О культуре» с данными из БД, а не из AI).

## 4. Миграция навигации на Navigation Compose

**Статус:** отложено.
**Дата обсуждения:** 2026-09-23.

### Контекст

Сейчас навигация реализована вручную через `var showXxx by remember`,
`if (...)` и `return`. Это работает, но:

- Много независимых флагов — легко забыть сбросить состояние.
- При повороте экрана состояние сбрасывается (лечим через
  `rememberSaveable`, но это костыль).
- Нет единой точки для логирования переходов, аналитики.

### Что даст миграция

- `NavHost` + `NavController` — единая точка управления экранами.
- Автоматическое сохранение состояния при повороте и сворачивании.
- Проще добавлять новые экраны и диплинки.

### Связанные файлы

- `MainActivity.kt` — там сейчас вся навигация.
- `app/build.gradle.kts` — добавить
  `androidx.navigation:navigation-compose:2.7.7+`.

## 7. Кэш ответов на стороне сервера → в персистентное хранилище

**Статус:** отложено.
**Дата обсуждения:** 2026-09-23.

### Контекст

Сейчас `server_cache` и `plan_cache` — обычные `dict` в памяти
процесса. При перезапуске Render (в том числе после cold start)
они обнуляются. На бесплатном тарифе Render контейнер засыпает
через 15 минут и перезапускается — кэш теряется.

### Что предлагается

- Подключить Redis (на Render есть аддон, но тоже засыпает на
  бесплатном тарифе).
- Или использовать SQLite/Postgres для персистентного кэша.
- Или вынести кэш на клиент полностью (Room уже работает).

### Приоритет

Низкий — пока пользователей мало, не критично.

## 8. Сохранение выбранного таба внутри CultureDetailScreen

**Статус:** отложено.
**Дата обсуждения:** 2026-09-23.

### Проблема

Внутри `CultureDetailScreen` пользователь выбирает один из табов:
Задачи / Уход / Вредители / Болезни / Заметки. При повороте экрана
Android пересоздаёт Activity, и вкладка сбрасывается на «Задачи».

Причина: `var selectedTab by remember { mutableStateOf(0) }` внутри
`CultureDetailScreen.kt`. Нужно заменить на `rememberSaveable`.

### Решение (при реализации)

В `CultureDetailScreen.kt` заменить:

    var selectedTab by remember { mutableStateOf(0) }

на:

    var selectedTab by rememberSaveable { mutableStateOf(0) }

Проверить, что импорт `androidx.compose.runtime.saveable.rememberSaveable`
добавлен. Всё остальное (список табов, when-блок) — не трогать.

### Связанные файлы

- `ui/CultureDetailScreen.kt` — строка с `var selectedTab`.

#### Ключевые слова для консоли RuStore (подготовка к следующему обновлению)

Приоритетный набор №1 (~96 символов с запятыми — под типовой лимит

  органично в текст, не перечислением.
- По мере выхода этапов 2–3 добавлять: дизайн участка, схема посадок,
  севооборот, визуализация сада — только после появления функций.

## 14. Санкционная устойчивость (работа из РФ)

**Принцип:** проект работает из России — доступ к западным сервисам
может блокироваться сетями РФ, их собственными geo-ограничениями или
становиться неоплачиваемым. Поэтому:

1. ПЕРЕД интеграцией любого нового сервиса в код — обязательные тесты
   доступности по чек-листу ниже. Без зелёных тестов сервис
   не интегрируется.
2. Западные модели (Google, OpenAI, Anthropic) — ТОЛЬКО через
   российские агрегаторы (AITunnel), напрямую API не вызываем никогда.
3. У каждой внешней зависимости должен быть назначен план Б.

Нюанс архитектуры: в проде DeepSeek/AITunnel вызываются с Render
(США), а не из РФ. Замеры из РФ важны для локальной разработки,
для `test.sh` и на случай переезда на RU-хостинг.

### Матрица зависимостей и рисков

Базовый замер: 2026-10-02, curl с машины разработчика (сеть РФ).

| Зависимость | Роль | Доступ из РФ (замер) | Риск | План Б |
|---|---|---|---|---|
| DeepSeek API | текст | да (401 без ключа = сервис отвечает) | низкий | агрегация через AITunnel |
| AITunnel | vision, буфер к Gemini/GPT/Claude, оплата в ₽ | да (401 = отвечает) | средний: зависимость от одного агрегатора | proxyapi.ru и аналоги |
| Render | хостинг бэкенда | да, 0,8 с | средний: США, платный тариф из РФ не оплатить, риск блокировки аккаунтов РФ | переезд на RU-хостинг (Timeweb / Selectel / Yandex Cloud) — FastAPI-приложение переносимо |
| GitHub | репозиторий | да (200) | средний | локальные бэкапы репозитория |
| RuStore Pay / VK Реклама / Яндекс.Директ | платежи и реклама | да (200) | низкий | — |
| PlantNet | определение вида растений | НЕТ — соединение не устанавливается (HTTP 000) | высокий | Gemini через AITunnel (уже определяет вид) |
| UptimeRobot | пинг против сна Render | да | низкий | RU-аналог (например, HostTracker) |

### Чек-лист перед интеграцией нового сервиса

      ответ любого HTTP-кода = доступен, 000 = блокировка).
- [ ] Доступность с хостинга бэкенда (Render; отдельный curl
      при переезде на VPS).
- [ ] Способ оплаты из РФ (карты РФ / агрегатор / крипта).
- [ ] Назначен fallback-провайдер (заполнить строку в матрице).
- [ ] Сценарий проверки добавлен в `test.sh`.

### Регулярная проверка (recurring, ежемесячно)

- [ ] Повторить curl-замеры по матрице, сверить с базовым замером.

## 16. Растение-питомец (тамагочи) для комнатных

**Статус:** отложено; кандидат на запуск параллельно с этапом 3
или сразу после него — эмоциональный крючок перед подпиской.
**Дата обсуждения:** 2026-10-06.

### Суть

Превратить комнатное растение из записи в справочнике в питомца:
кличка, фото, план ухода по фото, наблюдение динамики. Аргументы:

- Retention: утилиту открывают, когда случилась проблема; питомца
  проверяют каждый день.
- Сезонность: зимой сад спит, а фикусы живут — закрывает яму
  декабря–марта.
- Дёшево: инфраструктура готова (ask-photo определяет вид,
  indoor-промпт и генерация планов уже поддерживают комнатные).
- Рынок подтвердил механику (Planta, Blossom); в RuStore с русским
  AI-агрономом аналогов нет.

### MVP (1–2 недели на существующих блоках)

Реализация: PWA, 2026-10-06 (v14). Android — после валидации.

- [x] Фото + кличка при добавлении; photo-first: снимок → `/api/identify`
      → кандидаты → культура (source: AI_PHOTO), фото хранится с меткой
      IDENTIFY. Кличка (petName) — отдельное поле, приоритетна в поиске.
- [x] «День усыновления» и возраст: createdAt + подпись «с нами N дней»
      на карточке культуры.
- [x] Статус самочувствия: зелёный/жёлтый/красный по просроченным
      задачам полива (0 просрочек = зелёный, 1 = жёлтый, 2+ = красный,
      нет задач полива = серый). Точка в списке сада + подпись на карточке.
      Считается локально, ноль AI-запросов.
- [x] Фото-дневник растения: вкладка «История», фото GROWTH_LOG
      по датам (сетка миниатюр).
- [x] Стрики и достижения: «полив без пропусков» (закрытые вовремя
      задачи полива подряд, запас 1 сутки), бейджи «30 дней вместе»,
      «Полив без пропусков — неделя», «Первый урожай» (по HarvestLog).
      Без казино-механик.
- [ ] «Составить план по фото» одним шагом — сейчас двухшаговый флоу
      (фото → культура → план на вкладке «Задачи»); объединить в
      следующей партии UX-правок.
- [ ] Подсказка о хранении фото: приложение хранит собственную сжатую
      копию снимка (~640 px, IndexedDB), а не ссылку на галерею —
      удаление из галереи НЕ удаляет фото из приложения. Предупреждать
      об обратном: очистка данных сайта / удаление PWA стирает копии
      (установленное на «Домой» приложение на iOS защищено от
      7-дневной чистки Safari). Места: тост после первого
      добавленного фото + блок «Данные» в «Ещё» (краткая версия
      текста уже добавлена 2026-10-06).

### Вторая очередь (не реализовано, по триггерам)

- AI-контроль динамики: два фото в ОДНОМ vision-запросе
  («вырос, новая ветка, желтеет») — ~33 коп. раз в неделю-две.
- Реплики растения при открытии («жарко от батареи…») — взрослый тон,
  генерация дешёвыми запросами или шаблонами на клиенте.
- Локальные push-напоминания «полей меня» (iOS: Web Push 16.4+
  для установленных PWA — веб-версия тоже охватывается).
- Расширение на сад: «паспорт дерева-ветерана», счётчик урожая.

### Технические рамки

- Фото хранятся ТОЛЬКО локально (Room BLOB / IndexedDB) — политика
  конфиденциальности обещает отсутствие хранения на сервере; на AI
  уходит только в момент запроса.
- Интерактив не расходует дневной лимит: статус, стрики, напоминания —
  клиентская логика; AI — только по явному действию пользователя.
- Стоимость активного пользователя с еженедельным фото-контролем —
  ~1–2 ₽/мес; идеально ложится в подписку (этап 4) как
  «безлимит ухода за питомцами».

### Связанные файлы

- Сервер: без изменений (ask-photo, generate-plan уже умеют indoor).
- Android: `Culture` (+ petName, adoptedAt, photoUri), статусы задач.
- PWA: `js/db.js` (поля культуры), фото-дневник в карточке культуры.
